This topic describes how to use the MySQL connector.

## Background information

The MySQL connector supports all databases that are compatible with the MySQL protocol, including ApsaraDB RDS for MySQL, PolarDB for MySQL, OceanBase (MySQL mode), and self-managed MySQL databases.

**Important**

When you use the MySQL connector to read data from OceanBase, make sure that binary logging is enabled and properly configured in OceanBase. For more information, see [Binary logging operations](/help/en/apsaradb-for-oceanbase/latest/binlog-related-operations). This feature is in public preview. Evaluate its suitability and use it with caution before deployment.

The MySQL connector supports the following features.

**Details**

Source tables, dimension tables, and sink tables. Also supports data ingestion from data sources.

Streaming mode only

Not applicable

**Monitoring metrics**

-   Source table
    
    -   currentFetchEventTimeLag: The time difference between when a record is generated and when it is fetched by the Source Operator.

    -   currentEmitEventTimeLag: The time difference between when a record is generated and when it leaves the Source Operator.

## Key features

A MySQL CDC source table reads historical full data from the database first and then seamlessly switches to reading binary logs. This ensures no data is missed or duplicated. Even if failures occur, data processing guarantees exactly-once semantics. The MySQL CDC source table supports concurrent reading of full data and uses an incremental snapshot algorithm to achieve lockless operation and resumable transfers. For more information, see [About MySQL CDC source tables](#section-mxk-9ip-5kv).

-   Unified streaming and batch processing. Reads both full and incremental data without maintaining two separate workflows.
    
-   Concurrent reading of full data for horizontal scalability.
    
-   Seamless transition from full-data reading to incremental reading, with automatic scale-in to save compute resources.
    
-   Resumable transfers during full-data reading for improved stability.
    
-   Lockless reading of full data to avoid impacting online business.
    
-   Supports reading backup logs from ApsaraDB RDS for MySQL.
    
-   Parallel parsing of binary log files for lower latency.
    

## Prerequisites

Before using a MySQL CDC source table, complete the steps in [Configure MySQL](/help/en/flink/configure-a-mysql-database#concept-2116236). These steps ensure that your environment meets the prerequisites for using MySQL CDC source tables.

#### **ApsaraDB RDS for MySQL**

-   Perform [network connectivity testing](/help/en/flink/realtime-flink/support/faq-about-network-connectivity#c1e56cf164v5v) between ApsaraDB RDS for MySQL and Realtime Compute for Apache Flink to verify network connectivity.
    
-   MySQL version requirements: 5.6, 5.7, or 8.0.x.
    
-   Enable binary logging. (Enabled by default.)
    
-   Set the binary log format to ROW. (ROW is the default format.)
    
-   Set binlog\_row\_image to FULL. (FULL is the default setting.)
    
-   Disable Binary Log Transaction Compression. (Introduced in MySQL 8.0.20 and later. Disabled by default.)
    
-   A MySQL user has been created with SELECT, SHOW DATABASES, REPLICATION SLAVE, and REPLICATION CLIENT privileges.
    
-   Create a MySQL database and table. For more information, see [Create a database and account for ApsaraDB RDS for MySQL](/help/en/rds/create-databases-and-accounts-for-an-apsaradb-rds-for-mysql-instance#concept-jyq-tc5-q2b). Use a privileged account to create the database to prevent failures caused by insufficient permissions.
    
-   Configure an IP address whitelist. For more information, see [Configure an IP address whitelist for ApsaraDB RDS for MySQL](/help/en/rds/use-a-database-client-or-the-cli-to-connect-to-an-apsaradb-rds-for-mysql-instance-2#concept-pdr-k2f-vdb).

## Limits

#### **General limits**

-   MySQL CDC source tables do not currently support defining watermarks.
    
-   In CTAS and CDAS jobs, the MySQL CDC source table can synchronize some schema changes. For details about supported change types, see [Schema evolution synchronization policy](/help/en/flink/realtime-flink/developer-reference/create-table-as-statement#section-o1j-n87-aar).
    
-   The MySQL CDC connector does not support Binary Log Transaction Compression. When consuming incremental data, make sure this feature is disabled. Otherwise, incremental data may fail to load.
    

#### [**ApsaraDB RDS for MySQL**](https://www.aliyun.com/product/rds/mysql) **limits**

-   Do not read data from standby or read-only instances of ApsaraDB RDS for MySQL. Binary logs on these instances are retained for short periods by default. If binary logs expire and are cleaned up, jobs may fail to consume them.
    
-   ApsaraDB RDS for MySQL enables parallel replication by default but does not guarantee transaction order consistency between primary and secondary instances. After a primary/secondary switchover, checkpoint recovery may skip some data. To avoid this, enable the slave\_preserve\_commit\_order option in ApsaraDB RDS for MySQL.
    

#### [**PolarDB for MySQL**](https://www.aliyun.com/product/polardb/mysql) **limits**

The MySQL CDC source table does not support reading binary logs from multi-master clusters in PolarDB for MySQL versions 1.0.19 and earlier. ([What is a multi-master cluster?](/help/en/polardb/polardb-for-mysql/user-guide/multi-master-cluster-edition-database-or-table#title-sl7-ywy-lhh)) Binary logs from these clusters may contain duplicate table IDs, which can cause schema mapping errors and parsing failures.

#### [**Open-source MySQL**](https://www.mysql.com/) **limits**

By default, MySQL maintains transaction order during primary-replica binary log replication. If parallel replication is enabled on a MySQL replica ([slave\_parallel\_workers](https://dev.mysql.com/doc/refman/8.4/en/replication-options-replica.html#sysvar_slave_parallel_workers) > 1) but [slave\_preserve\_commit\_order](https://dev.mysql.com/doc/refman/8.4/en/replication-options-replica.html#sysvar_slave_preserve_commit_order) = ON is not enabled, the transaction commit order may not match that of the primary database. This out-of-order commit behavior can cause data loss when Flink CDC resumes from a checkpoint. To prevent this issue, we recommend setting `slave_preserve_commit_order` = ON on the MySQL replica. Alternatively, you can set `slave_parallel_workers` = 1, which sacrifices replication performance.

## Important notes

-   Each MySQL CDC data source must have a unique server ID.
    
    #### **Purpose of server ID**
    
    Each MySQL CDC data source must have a unique server ID. If multiple data sources share the same server ID and cannot reuse connections, binary log offsets may become inconsistent, leading to missing or duplicated data.
    
    #### **Server ID configuration for different scenarios**
    
    You can specify the server ID in DDL statements, but we recommend using [dynamic hints](https://ci.apache.org/projects/flink/flink-docs-release-1.11/dev/table/sql/hints.html) instead of DDL parameters.
    
    -   **Degree of parallelism = 1 or incremental snapshots disabled**
        
        ```
        ## Specify a specific server ID when incremental snapshots are disabled or degree of parallelism is 1.
        SELECT * FROM source_table /*+ OPTIONS('server-id'='123456') */ ;
        ```
        
    -   **Degree of parallelism > 1 and incremental snapshots enabled**
        
        ```
        ## Specify a range of server IDs. Ensure the number of available IDs in the range is at least equal to the degree of parallelism. For example, if the degree of parallelism is 3:
        SELECT * FROM source_table /*+ OPTIONS('server-id'='123456-123458') */ ;
        ```
        
    -   **Data synchronization using CTAS**
        
        When synchronizing data using CTAS, if the CDC data sources have identical configurations, they are automatically reused. In this case, you can assign the same server ID to multiple CDC data sources. For more information, see [Example 4: Multiple CTAS statements](/help/en/flink/realtime-flink/developer-reference/create-table-as-statement#section-cnf-jio-mw2).
        
    -   **Multiple non-CTAS source tables that cannot be reused**
        
        If your job contains multiple MySQL CDC source tables and does not use CTAS, data sources cannot be reused. Assign a unique server ID to each CDC source table. Similarly, if incremental snapshots are enabled and the degree of parallelism is greater than 1, specify a server ID range.
        
        ```
        select * from 
          source_table1 /*+ OPTIONS('server-id'='123456-123457') */
        left join 
          source_table2 /*+ OPTIONS('server-id'='123458-123459') */
        on source_table1.id=source_table2.id;
        ```
        
    

-   **Sink tables**
    
    -   Auto-increment primary keys are not declared in DDL. MySQL fills them automatically during data writes.
        
    -   At least one non-primary-key field must be declared. Otherwise, an error occurs.
        
    -   NOT ENFORCED in DDL means Flink does not enforce primary key validation. You must ensure primary key correctness and integrity. For more information, see [Validity check](https://nightlies.apache.org/flink/flink-docs-master/docs/dev/table/sql/create/#primary-key).
        
-   **Dimension tables**
    
    To accelerate queries using indexes, the JOIN condition fields must match the index definition order (leftmost prefix rule). For example, if the index is (a, b, c), the JOIN condition should be `ON t.a = x AND t.b = y`.
    
    > Flink-generated SQL may be rewritten by the optimizer, preventing index usage. To confirm whether indexes are used, check the execution plan (EXPLAIN) or slow query logs in MySQL for the actual SELECT statement executed.
    

## SQL

You can use the MySQL connector in SQL jobs as a source table, dimension table, or sink table.

### **Syntax**

```
CREATE TEMPORARY TABLE mysqlcdc_source (
   order_id INT,
   order_date TIMESTAMP(0),
   customer_name STRING,
   price DECIMAL(10, 5),
   product_id INT,
   order_status BOOLEAN,
   PRIMARY KEY(order_id) NOT ENFORCED
) WITH (
  'connector' = 'mysql',
  'hostname' = '<yourHostname>',
  'port' = '3306',
  'username' = '<yourUsername>',
  'password' = '<yourPassword>',
  'database-name' = '<yourDatabaseName>',
  'table-name' = '<yourTableName>'
);
```

**Note**

-   How the connector writes to sink tables: Each incoming record is converted into an INSERT statement and executed. The exact SQL depends on the scenario:
    
    -   For sink tables without primary keys, the connector executes `INSERT INTO table_name (column1, column2, ...) VALUES (value1, value2, ...);`.
        
    -   For sink tables with primary keys, the connector executes `INSERT INTO table_name (column1, column2, ...) VALUES (value1, value2, ...) ON DUPLICATE KEY UPDATE column1 = VALUES(column1), column2 = VALUES(column2), ...;`. Note: If the physical table has a unique index constraint other than the primary key, inserting two records with different primary keys but identical unique index values causes data loss due to conflicts.
        
-   If your MySQL database defines an auto-increment primary key, do not declare it in the Flink DDL. MySQL fills this field automatically during data writes. The connector supports writing and deleting data with auto-increment fields but does not support updates.

## About MySQL CDC source tables

-   **Implementation principles**
    
    When a MySQL CDC source table starts, it scans the entire table, dividing it into multiple chunks based on the primary key, and records the binary log offset. It then reads data from each chunk sequentially using an incremental snapshot algorithm with SELECT statements. The job periodically performs checkpoints, recording completed chunks. In case of failover, it resumes reading from uncompleted chunks. After all chunks are read, it reads incremental change records from the previously recorded binary log offset. The Flink job continues to perform checkpoints periodically, recording the binary log offset. If the job fails over, it resumes processing from the last recorded binary log offset, ensuring exactly-once semantics.
    
    For a more detailed explanation of the incremental snapshot algorithm, see [MySQL CDC Connector](https://nightlies.apache.org/flink/flink-cdc-docs-release-3.1/docs/connectors/flink-sources/mysql-cdc/).
    
-   **Metadata**
    
    Metadata is useful in sharding scenarios where you merge and synchronize data from multiple databases and tables. In such cases, you often need to distinguish the source database and table for each record. [Metadata columns](https://nightlies.apache.org/flink/flink-docs-release-1.14/docs/dev/table/sql/create/#columns) provide access to the source table's database and table name information, making it easy to merge multiple sharded tables into a single destination table.
    
    The MySQL CDC Source supports metadata column syntax, allowing you to access the following metadata:
    
    **Metadata key**
    
    **Metadata type**
    
    **Description**
    
    database\_name
    
    STRING NOT NULL
    
    The database name containing the record.
    
    table\_name
    
    STRING NOT NULL
    
    The table name containing the record.
    
    op\_ts
    
    TIMESTAMP\_LTZ(3) NOT NULL
    
    The change time of the record in the database. If the record comes from historical data rather than binary logs, this value is always 0.
    
    op\_type
    
    STRING NOT NULL
    
    The change type of the record.
    
    -   +I: INSERT message
        
    -   \-D: DELETE message
        
    -   \-U: UPDATE\_BEFORE message
        
    -   +U: UPDATE\_AFTER message
        
    
    **Note**
    
    Supported only in VVR 8.0.7 and later.
    
    query\_log
    
    STRING NOT NULL
    
    The MySQL query log record corresponding to the row.
    
    **Note**
    
    MySQL must have the binlog\_rows\_query\_log\_events parameter enabled to record query logs.
    
    The following code example merges multiple sharded orders tables from different databases in a MySQL instance into a single holo\_orders table in Hologres.
    
    ```
    CREATE TEMPORARY TABLE mysql_orders (
      db_name STRING METADATA FROM 'database_name' VIRTUAL,  -- Read database name.
      table_name STRING METADATA  FROM 'table_name' VIRTUAL, -- Read table name.
      operation_ts TIMESTAMP_LTZ(3) METADATA FROM 'op_ts' VIRTUAL, -- Read change time.
      op_type STRING METADATA FROM 'op_type' VIRTUAL, -- Read change type.
      order_id INT,
      order_date TIMESTAMP(0),
      customer_name STRING,
      price DECIMAL(10, 5),
      product_id INT,
      order_status BOOLEAN,
      PRIMARY KEY(order_id) NOT ENFORCED
    ) WITH (
      'connector' = 'mysql-cdc',
      'hostname' = 'localhost',
      'port' = '3306',
      'username' = 'flinkuser',
      'password' = 'flinkpw',
      'database-name' = 'mydb_.*', -- Regex match multiple sharded databases.
      'table-name' = 'orders_.*'   -- Regex match multiple sharded tables.
    );
    
    INSERT INTO holo_orders SELECT * FROM mysql_orders;
    ```
    
    Based on the preceding code, if you set the scan.read-changelog-as-append-only.enabled parameter to true in the WITH clause, the output varies based on the sink table's primary key configuration:
    
    -   If the sink table's primary key is order\_id, the output contains only the last change for each primary key from the source table. For a primary key whose last change was a delete operation, the sink table shows a record with the same primary key and an op\_type of -D.
        
    -   If the sink table's primary key is order\_id, operation\_ts, and op\_type, the output contains the complete change history for each primary key from the source table.
        
    
-   **Regular expression support**
    
    The MySQL CDC source table supports using regular expressions in table names or database names to match multiple tables or databases. The following code example uses regular expressions to specify multiple tables.
    
    ```
    CREATE TABLE products (
      db_name STRING METADATA FROM 'database_name' VIRTUAL,
      table_name STRING METADATA  FROM 'table_name' VIRTUAL,
      operation_ts TIMESTAMP_LTZ(3) METADATA FROM 'op_ts' VIRTUAL,
      order_id INT,
      order_date TIMESTAMP(0),
      customer_name STRING,
      price DECIMAL(10, 5),
      product_id INT,
      order_status BOOLEAN,
      PRIMARY KEY(order_id) NOT ENFORCED
    ) WITH (
      'connector' = 'mysql-cdc',
      'hostname' = 'localhost',
      'port' = '3306',
      'username' = 'root',
      'password' = '123456',
      'database-name' = '(^(test).*|^(tpc).*|txc|.*[p$]|t{2})', -- Regex match multiple databases.
      'table-name' = '(t[5-8]|tt)' -- Regex match multiple tables.
    );
    ```
    
    Explanation of the regular expressions in the example:
    
    -   ^(test).\* is a prefix matching example. This expression matches database names starting with "test", such as test1 or test2.
        
    -   .\*\[p$\] is a suffix matching example. This expression matches database names ending with "p", such as cdcp or edcp.
        
    -   txc is an exact match. This matches the database name "txc".
        
    
    When matching full-path table names, MySQL CDC uniquely identifies a table using the database name and table name, i.e., database-name.table-name as the matching pattern. For example, the pattern (^(test).\*|^(tpc).\*|txc|.\*\[p$\]|t{2}).(t\[5-8\]|tt) can match tables txc.tt and test2.test5 in the database.
    
    **Important**
    
    In SQL job configurations, table-name and database-name do not support comma-separated lists for specifying multiple tables or databases.
    
    -   To match multiple tables or use multiple regular expressions, connect them with a vertical bar (|) and enclose them in parentheses. For example, to read tables 'user' and 'product', set table-name to `(user|product)`.
        
    -   If a regular expression contains a comma, rewrite it using the vertical bar (|) operator. For example, rewrite `mytable_\d{1, 2}` as the equivalent `(mytable_\d{1}|mytable_\d{2})` to avoid using commas.
        
    
-   **Concurrency control**
    
    The MySQL connector supports concurrent reading of full data to improve data loading efficiency. Combined with the Autopilot auto-tuning feature in the Flink Realtime Compute console, it automatically scales down during the incremental phase after concurrent full-data reading, saving compute resources.
    
    In the Realtime Compute development console, you can set the job's degree of parallelism in basic or expert mode. The difference in setting concurrency is as follows:
    
    -   The concurrency set in basic mode applies globally to the job.![基础模式](https://help-static-aliyun-doc.aliyuncs.com/assets/img/en-US/8620965361/p328894.png)
        
    -   In expert mode, you can set the degree of parallelism for specific vertices.![vertex并发](https://help-static-aliyun-doc.aliyuncs.com/assets/img/en-US/8665409761/p328899.png)
        
    
    For more information about resource configuration, see [Configure job deployment information](/help/en/flink/realtime-flink/user-guide/configure-a-deployment#task-2101351).
    
    **Important**
    
    Regardless of the mode, when setting concurrency, the server-id range declared in the table must be greater than or equal to the job's degree of parallelism. For example, if the server-id range is 5404-5412, there are 8 unique server IDs, so the job can have a maximum of 8 concurrent tasks. Different jobs accessing the same MySQL instance must have non-overlapping server-id ranges; each job must explicitly configure a unique server-id.
    
-   **Autopilot auto-scaling**
    
    The full data phase accumulates a large amount of historical data. To improve reading efficiency, concurrent reading is typically used. In the binary log incremental phase, because binary log data volume is small and to ensure global order, single-threaded reading is usually sufficient. The different resource requirements for the full and incremental phases can be automatically balanced by the auto-tuning feature.
    
    Auto-tuning monitors the traffic of each task in the MySQL CDC Source. When the job enters the binary log phase, if only one task is responsible for binary log reading and other tasks are idle, auto-tuning automatically reduces the Source's CU count and concurrency. To enable auto-tuning, set the auto-tuning mode to Active on the job operations page.
    
    **Note**
    
    The minimum trigger interval for reducing concurrency is 24 hours by default. For more information about auto-tuning parameters and details, see [Configure auto-tuning](/help/en/flink/realtime-flink/user-guide/configure-autopilot-and-scheduled-tuning#task-2563742).
    
-   **Startup modes**
    
    Use the scan.startup.mode configuration item to specify the startup mode for the MySQL CDC source table. Valid values:
    
    -   **initial (default)**: On first startup, performs a full read of the database table, then switches to incremental binary log reading.
        
    -   **earliest-offset**: Skips the snapshot phase and starts reading from the earliest available binary log offset.
        
    -   **latest-offset**: Skips the snapshot phase and starts reading from the end of the binary log. In this mode, the source table only reads data changes that occur after the job starts.
        
    -   **specific-offset**: Skips the snapshot phase and starts reading from a specified binary log offset. The offset can be specified by binary log filename and position, or by a GTID set.
        
    -   **timestamp**: Skips the snapshot phase and starts reading binary log events from a specified timestamp.
        
    
    Example usage:
    
    ```
    CREATE TABLE mysql_source (...) WITH (
        'connector' = 'mysql-cdc',
        'scan.startup.mode' = 'earliest-offset', -- Start from the earliest offset.
        'scan.startup.mode' = 'latest-offset', -- Start from the latest offset.
        'scan.startup.mode' = 'specific-offset', -- Start from a specific offset.
        'scan.startup.mode' = 'timestamp', -- Start from a specific timestamp.
        'scan.startup.specific-offset.file' = 'mysql-bin.000003', -- Specify the binary log filename for specific-offset mode.
        'scan.startup.specific-offset.pos' = '4', -- Specify the binary log position for specific-offset mode.
        'scan.startup.specific-offset.gtid-set' = '24DA167-0C0C-11E8-8442-00059A3C7B00:1-19', -- Specify the GTID set for specific-offset mode.
        'scan.startup.timestamp-millis' = '1667232000000' -- Specify the startup timestamp for timestamp mode.
        ...
    )
    ```
    
    **Important**
    
    -   The MySQL source prints the current offset at checkpoint time with INFO level logging. The log prefix is `Binlog offset on checkpoint {checkpoint-id}`. This log helps you start the job from a specific checkpoint offset.
        
    -   If the table being read has undergone schema changes, starting from the earliest-offset, specific-offset, or timestamp modes may cause errors. This is because the Debezium reader internally maintains the latest table schema, and earlier data with mismatched schemas cannot be parsed correctly.
        
    

-   **About keyless CDC source tables**
    
    -   Using keyless tables requires setting scan.incremental.snapshot.chunk.key-column, and the selected column must be non-nullable.
        
    -   The processing semantics of keyless CDC source tables are determined by the behavior of the column specified in scan.incremental.snapshot.chunk.key-column:
        
        -   If the specified column is not updated, exactly-once semantics are guaranteed.
            
        -   If the specified column is updated, only at-least-once semantics are guaranteed. However, you can ensure data correctness by specifying a primary key in the downstream system and using idempotent operations.
            
-   **Reading Alibaba Cloud ApsaraDB RDS for MySQL backup logs**
    
    The MySQL CDC source table supports reading backup logs from Alibaba Cloud ApsaraDB RDS for MySQL. This is useful when the full data phase takes a long time, local binary log files are automatically cleaned up, but automatically or manually uploaded backup files still exist.
    
    Example usage:
    
    ```
    CREATE TABLE mysql_source (...) WITH (
        'connector' = 'mysql-cdc',
        'rds.region-id' = 'cn-beijing',
        'rds.access-key-id' = 'xxxxxxxxx', 
        'rds.access-key-secret' = 'xxxxxxxxx', 
        'rds.db-instance-id' = 'rm-xxxxxxxxxxxxxxxxx', 
        'rds.main-db-id' = '12345678',
        'rds.download.timeout' = '60s'
        ...
    )
    ```
    
-   **Enabling CDC Source reuse**
    
    In a single job, multiple MySQL CDC source tables start multiple Binlog clients. When all source tables are in the same instance, this increases the load on the database. For more information, see [MySQL CDC FAQ](/help/en/flink/realtime-flink/support/faq-about-cdc#e48efe1cfdne7).
    
    **Solution**
    
    VVR 8.0.7 and later supports MySQL CDC Source reuse. Reuse merges MySQL CDC source tables that can be combined. Merging occurs when source table configurations are identical, except for the database name, table name, and `server-id`. The engine automatically merges MySQL CDC sources within the same job.
    
    **Procedure**
    
    1.  Use the `SET` command in your SQL job:
        
        ```
        SET 'table.optimizer.source-merge.enabled' = 'true';
        
        # (VVR 8.0.8 and 8.0.9) Additionally set this:
        SET 'sql-gateway.exec-plan.enabled' = 'false';
        ```
        
        > **VVR 11.1 and later have reuse enabled by default.**
        
    2.  **Start the job stateless.** Modifying Source reuse configurations changes the job topology. You must start the job stateless. Otherwise, the job may fail to start or lose data. If Sources are merged, you will see a `MergetableSourceScan` node.
        
    
    **Important**
    
    -   After enabling reuse, we recommend not disabling operator chaining. Setting `pipeline.operator-chaining` to `false` increases data serialization and deserialization overhead. The more Sources merged, the greater the overhead.
        
    -   In VVR 8.0.7, disabling operator chaining causes serialization issues.
        
    

## **Accelerate binary log reading**

When the MySQL connector is used as a source table or data ingestion source, it parses binary log files to generate various change messages during the incremental phase. Binary log files record all table changes in binary format. Accelerate binary log file parsing using the following methods:

-   Enable parsing filter configuration
    
    -   Use the configuration item `scan.only.deserialize.captured.tables.changelog.enabled`: Only parse change events for specified tables.
        
-   Optimize Debezium parameters
    
    ```
    debezium.max.queue.size: 162580
    debezium.max.batch.size: 40960
    debezium.poll.interval.ms: 50
    ```
    
    -   `debezium.max.queue.size`: The maximum number of records the blocking queue can hold. When Debezium reads an event stream from the database, it places events into a blocking queue before writing them downstream. The default value is 8192.
        
    -   `debezium.max.batch.size`: The maximum number of events the connector processes in each iteration. The default value is 2048.
        
    -   `debezium.poll.interval.ms`: The number of milliseconds the connector waits before requesting new change events. The default value is 1000 milliseconds (1 second).
        

Example usage:

```
CREATE TABLE mysql_source (...) WITH (
    'connector' = 'mysql-cdc',
    -- Debezium configuration
    'debezium.max.queue.size' = '162580',
    'debezium.max.batch.size' = '40960',
    'debezium.poll.interval.ms' = '50',
    -- Enable parsing filter
    'scan.only.deserialize.captured.tables.changelog.enabled' = 'true',  -- Only parse change events for specified tables.
    ...
)
```

```
source:
  type: mysql
  name: MySQL Source
  hostname: ${mysql.hostname}
  port: ${mysql.port}
  username: ${mysql.username}
  password: ${mysql.password}
  tables: ${mysql.source.table}
  server-id: 7601-7604
  # Debezium configuration
  debezium.max.queue.size: 162580
  debezium.max.batch.size: 40960
  debezium.poll.interval.ms: 50
  # Enable parsing filter
  scan.only.deserialize.captured.tables.changelog.enabled: true
```

The enterprise version of MySQL CDC has a binary log consumption capacity of 85 MB/s, which is approximately twice that of the open-source community version. If the binary log generation rate exceeds 85 MB/s (i.e., a 512 MB file every 6 seconds), Flink job latency continuously increases. Latency gradually decreases when the binary log generation rate drops. If a binary log file contains a large transaction, processing latency may briefly increase, then decrease after the transaction's logs are processed.

Create a DataStream API program and use MySqlSource. The following provides code and pom dependency examples:

Java

```
import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import com.ververica.cdc.debezium.JsonDebeziumDeserializationSchema;
import com.ververica.cdc.connectors.mysql.source.MySqlSource;
public class MySqlSourceExample {
  public static void main(String[] args) throws Exception {
    MySqlSource<String> mySqlSource = MySqlSource.<String>builder()
        .hostname("yourHostname")
        .port(yourPort)
        .databaseList("yourDatabaseName") // set captured database
        .tableList("yourDatabaseName.yourTableName") // set captured table
        .username("yourUsername")
        .password("yourPassword")
        .deserializer(new JsonDebeziumDeserializationSchema()) // converts SourceRecord to JSON String
        .build();
    StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
    // enable checkpoint
    env.enableCheckpointing(3000);
    env
      .fromSource(mySqlSource, WatermarkStrategy.noWatermarks(), "MySQL Source")
      // set 4 parallel source tasks
      .setParallelism(4)
      .print().setParallelism(1); // use parallelism 1 for sink to keep message ordering
    env.execute("Print MySQL Snapshot + Binlog");
  }
}
```
