## What do I do if an error ODPS-0123131 appears when a custom extractor reads unstructured data that contains a data field of the DATETIME type?

-   Problem description
    
    When a custom extractor reads unstructured data, the following error message appears if a data field is of the DATETIME type, such as 2019-11-11 06:43:36.
    
    ```
    FAILED: ODPS-0123131:User defined function exception - Traceback:
    java.lang.IllegalArgumentException
        at java.sql.Date.valueOf(Date.java:143)
        at com.aliyun.odps.udf.example.text.TextExtractor.textLineToRecord(TextExtractor.java:194)
        at com.aliyun.odps.udf.example.text.TextExtractor.extract(TextExtractor.java:153)
        at com.aliyun.odps.udf.ExtractorHandler.extract(ExtractorHandler.java:120)       
    ```
    
-   Cause
    
    The `java.sql.Date.valueOf()` function in `Date.valueOf(parts[i])` at the specified position of the code supports only parameters of the STRING type, such as `"yyyy-[m]m-[d]d"`. This function does not support parameters of the DATETIME type.
    
-   Solution
    
    1.  Introduce the Joda-Time dependency and add import information to the code.
        
        ```
        -- Introduce the Joda-Time dependency. 
        <dependency>
          <groupId>joda-time</groupId>
          <artifactId>joda-time</artifactId>
          <version>2.10</version>
        </dependency> 
        -- Add import information. 
        import org.joda.time.DateTime;
        import org.joda.time.format.DateTimeFormat;                           
        ```
        
    2.  Add the `DateTimeFormat.forPattern()` function to convert the field of the DATETIME type into the STRING type for reading.
        
        ```
        record.setDate(index, new Date(DateTime.parse(parts[i], DateTimeFormat.forPattern("yyyy-MM-dd HH:mi:ss")).getMillis()));                           
        ```
        
    
    Example
    
    1.  Upload the JAR file that is generated by packaging the extractor project on the MaxCompute client.
        
        ```
        add jar /Users/gary/big_data/odps/text_extractor/target/text_extractor-1.0-SNAPSHOT.jar      
        ```
        
        `/Users/gary/big_data/odps/text_extractor/target/text_extractor-1.0-SNAPSHOT.jar` is the local directory for storing the generated JAR file.
        
    2.  Upload the Joda-Time third-party JAR file on the MaxCompute client.
        
        ```
        add jar /Users/gary/.m2/repository/joda-time/joda-time/2.10/joda-time-2.10.jar                         
        ```
        
        `/Users/gary/.m2/repository/joda-time/joda-time/2.10/joda-time-2.10.jar` is the local directory for storing the Joda-Time third-party JAR file.
        
    3.  Upload test data to the specified directory in OSS. In this example, the file name is `video_play_log.txt`. Sample data:
        
        ```
        5c661071dba64d5080c91da085ff1073^Music-Click-Fast Forward^26.12.04.68^2019-11-11 06:43:36                           
        ```
        
    4.  Read data from the external table.
        
        ```
        select * from <project_name>.video_play_log;
        ```
        
        Returned result:
        
        ```
        +------+-------+---+----------------+
        | uuid  | action  | ip  | time      |
        +------+-------+---+----------------+
        | 5c661071dba64d5080c91da085ff1073 | Music-Click-Fast Forward | 26.12.04.68 | 2019-11-11 06:43:36 |
        +------+-------+---+----------------+     
        ```
        

## After I upload a UDF that passes the local test when I use MaxCompute to access an OSS external table, a memory overflow error occurs. What do I do?

-   Problem description
    
    After I upload a UDF that passes the local test when I use MaxCompute to access an OSS external table, the following error message appears:
    
    ```
    FAILED: ODPS-0123131:User defined function exception - Traceback:
    java.lang.OutOfMemoryError: Java heap space        
    ```
    
    After I add the following configurations, the runtime increases but the error persists.
    
    ```
    set odps.stage.mapper.mem = 2048; 
    set odps.stage.mapper.jvm.mem = 4096;       
    ```
    
-   Cause
    
    The external table has an excessive number of objects, which occupy large memory space. In addition, no partitions are specified for the objects.
    
-   Solutions
    
    -   Query a small amount of data.
        
    -   Specify partitions for the objects to reduce memory usage.
        

## What do I do if the error message "Inline data exceeds the maximum allowed size" appears when I use an external table to process OSS data?

-   Problem description
    
    When MaxCompute processes OSS data, the error message `Inline data exceeds the maximum allowed size` appears.
    
-   Cause
    
    OSS storage limits the size of each object. If the size of an object exceeds 3 GB, an error occurs.
    
-   Solution
    
    Modify the configuration of the following properties to adjust the execution plan. The properties are used to manage the size of data that each reducer can write to an OSS external table. This helps ensure that the OSS storage object does not exceed 3 GB in size.
    
    ```
    set odps.sql.mapper.split.size=256; # Adjust the size of data that is read by each mapper. Unit: MB. 
    set odps.stage.reducer.num=100; # Adjust the number of workers in the reduce phase.
    ```

## How do I use an OSS external table to export multiple small files as one file?

Check whether a reducer or a joiner is used in the last step of the SQL execution plan in LogView logs. If a reducer is used in the last step, run the `set odps.stage.reducer.num=1;` command. If a joiner is used in the last step, run the `set odps.stage.joiner.num=1;` command.

## **What do I do if the ODPS-0130071 error is reported when I use MaxCompute to directly read Hologres data?**

-   Problem description
    
    When I directly read Hologres data, the "ODPS-0130071 Failed to split to equal size...max count: 7777" error message is reported. Example:
    
    ```
    ODPS-0130071:[0,0] Semantic analysis exception - physical plan generation failed: storage/table/src/input_splits_builder.cpp(195): StorageException: Failed to split to equal size, total size: 2143570729934, min size: 268435456, max size: 272629760, max count: 7777, split size: 275629513, split count: 7777
    ```
    
-   Cause
    
    When MaxCompute reads Hologres data directly, it uses the default Mapper splitting strategy (input data size/split.size of 256 MB). This results in the number of Mappers exceeding the maximum limit of 7777. 
    
    **Note**
    
    This restriction is in place to prevent users from directly submitting tasks that generate a large number of Mappers, which can affect the stability of Hologres files or network connections.
    
-   Solution
    
    You can resolve this issue by configuring the following parameters:
    
    ```
    SET odps.external.holo.mapper.instances=10000; --Increase the upper limit of concurrency to 10000.
    SET odps.sql.mapper.split.size=512; --Adjust the task concurrency by increasing the split size to 512 MB.
    ```
    

## What do I do if an SQL job runs slowly based on an external table?

When an SQL job runs based on an external table, the job may run slowly due to one of the following reasons:

-   Slow reading of a GZIP compression file from an OSS external table
    
    -   Problem description
        
        An OSS external table is created. The data source is a GZIP compression file in OSS and the file size is 200 GB. The execution is slow during data reading.
        
    -   Cause
        
        SQL statement execution is slow because the number of mappers that are used to perform computing is excessively small.
        
    -   Solution
        
        -   For structured data, you can configure the odps.sql.mapper.split.size parameter to adjust the amount of data read by a single mapper to accelerate SQL statement execution.
            
            ```
            set odps.sql.mapper.split.size=256; # Adjust the size of table data that is read by each mapper. Unit: MB.        
            ```
            
        -   For unstructured data, you must check whether only one OSS file is stored in the directory of the OSS external table. If only one OSS file exists, only one mapper can be generated because unstructured data cannot be split in compression mode. This results in slow data processing. We recommend that you split a large OSS file into small files in the directory of the OSS external table. This helps increase the number of mappers generated to read the external table and increase the read speed.
            
-   Slow search of data in an external table by using MaxCompute SDK
    
    -   Problem description
        
        MaxCompute SDK searches for data in an external table at a low speed.
        
    -   Solution
        
        External tables support only full search. The search speed is slow. We recommend that you use a MaxCompute internal table instead of the external table for the search.
        
-   Slow data query from a Tablestore external table
    
    -   Problem description
        
        Data is queried from a Tablestore external table at a low speed. If the same business data is written to a Tablestore external table in real time and periodically written to a MaxCompute internal table, and the two tables have the same schema and data volume, the time required to query data in the MaxCompute internal table is much less than the time required to query data in the Tablestore external table.
        
    -   Solution
        
        The data may be computed multiple times. As a result, the data query is slow. To improve query efficiency in this scenario, you can import required data to a MaxCompute internal table and then query the data in the internal table. This method is more efficient than reading data from Tablestore each time data is queried.
        

## What do I do if the "**Couldn't connect to server**" error is reported when I read data from an **OSS external table?**

-   Problem description
    
    When I read data from an OSS external table, the following error is reported: `ODPS-0123131:User defined function exception - common/io/oss/oss_client.cpp(95): OSSRequestException: req_id: , http status code: -998, error code: HttpIoError, message: Couldn't connect to server`.
    
-   Causes
    
    -   Cause 1: `oss_endpoint` in the `oss_location` parameter used when you create the OSS external table points to a public endpoint, instead of an internal endpoint.
        
    -   Cause 2: `oss_endpoint` in the `oss_location` parameter used when you create the OSS external table points to an endpoint in a different region.
        
-   Solutions
    
    -   For Cause 1:
        
        Check `oss_endpoint` in the `oss_location` parameter of your external table creation statement. If it uses a public endpoint, change it to the corresponding internal endpoint. For more parameter information, see [Parameters](/help/en/maxcompute/user-guide/access-external-tables/#5ca59599e4lgp).
        
        For example, if you use `oss://oss-ap-southeast-5.aliyuncs.com/<bucket>/....` to create an external table in the Indonesia (Jakarta) region, change it to the internal endpoint `oss://oss-ap-southeast-5-internal.aliyuncs.com/<bucket>/....`.
        
    -   For Cause 2:
        
        Verify that `oss_endpoint` in the `oss_location` parameter in the external table creation statement corresponds to the endpoint of the region where you want to access. For more information about OSS endpoints in different regions, see [Regions and endpoints](/help/en/oss/user-guide/regions-and-endpoints#concept-zt4-cvy-5db).
        

## What do I do if the "**Network is unreachable (connect failed)**" error is reported when I create an **OSS external table?**

-   Problem description
    
    When I create an OSS external table, the following error is reported: `ODPS-0130071:[1,1] Semantic analysis exception - external table checking failure, error message: Cannot connect to the endpoint 'oss-cn-beijing.aliyuncs.com': Connect to bucket.oss-cn-beijing.aliyuncs.com:80 [bucket.oss-cn-beijing.aliyuncs.com] failed: Network is unreachable (connect failed)`.
    
-   Cause
    
    When you create the OSS external table, `oss_endpoint` in the `oss_location` parameter points to a public endpoint, instead of an internal endpoint.
    
-   Solution
    
    Verify that `oss_endpoint` in the `oss_location` parameter in the external table creation statement points to an internal endpoint. If a public endpoint is used, change it to an internal endpoint. For more parameter information, see [Parameters](/help/en/maxcompute/user-guide/access-external-tables/#5ca59599e4lgp).
    
    For example, if you use `oss://oss-cn-beijing.aliyuncs.com/<bucket>/....` to create an external table in the China (Beijing) region, change it to the internal endpoint `oss://oss-cn-beijing-internal.aliyuncs.com/<bucket>/....`.
